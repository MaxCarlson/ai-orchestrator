## Architecture proposal

**v1 for the next one to two passes** should keep your existing physical architecture and improve retrieval quality with the smallest set of structural additions. Concretely: keep `code_chunks`, `text_chunks`, and `memory_items` as separate stores; add PostgreSQL FTS (`tsvector` + GIN) over code and text chunks; keep pgvector dense retrieval; fuse lexical and dense with RRF; optionally rerank only the top 20–50 results; and expose a single logical retrieval service that delegates internally to code/text/memory retrievers. This matches the repo’s existing split schema and hybrid retrieval direction, while aligning with the strongest practical retrieval pattern in both engineering docs and research: hybrid first stage plus reranking. PostgreSQL itself recommends GIN for text search; Sentence Transformers documents retrieve-then-rerank explicitly; and BGE-M3’s own guidance recommends hybrid retrieval plus reranking. fileciteturn7file1 fileciteturn8file3 citeturn33view0turn17view0turn19view2

For code chunking in v1, I would move from “generic AST chunks” to **symbol-first chunking with structural sidecars**. That means: emit a chunk for each top-level function/method/class; emit a module/file summary chunk; emit an import/config/header chunk; emit targeted test chunks; and attach cheap metadata: `language`, `path`, `module`, `symbol_kind`, `symbol_name`, `qualified_name`, `parent_symbol`, `start_line`, `end_line`, `imports`, `exports`, `is_test`, and, where easy, `doc_path` or `readme_section`. Tree-sitter is the right extraction substrate here because it is incremental, language-agnostic, and queryable by typed node structure. For this repo, start with Python, TypeScript/TSX, and shell; JSON/YAML/config can follow as text-first artifacts. citeturn16view0turn16view1turn16view2

For code retrieval in v1, I would not jump straight to a full graph database. Instead, add two small relational tables: `repo_symbols` and `repo_edges`. The important edge kinds are `defines`, `imports`, `calls`, `inherits`, `tests`, and `documents`. Use them for **post-retrieval expansion**, not as the first-stage search engine. The retrieval flow should become: classify the query as code/text/memory/mixed; retrieve anchors lexically + densely; expand one or two hops along selected edge kinds; rerank the combined shortlist; then package context as a handful of chunks plus one or two file/module summaries. The recent repository-level literature strongly supports this shape: graph-augmented retrieval and hierarchical repo maps consistently outperform flat chunk retrieval when the task is repository understanding rather than snippet similarity. citeturn30academia6turn36academia0turn36academia2turn36academia3turn30academia3

**v2 after first successful indexing/search proof** should deepen quality rather than widen infrastructure. At that point, add project-note ingestion and promotion-to-memory workflows; add a `kind` taxonomy on durable memories; introduce query-intent-specific retrieval weights; materialize per-module and per-project “repo map” summaries; and add an assigner loop with priority escalation when chat, search, or `aioc` requests arrive for a project whose embeddings are stale or missing. This is also the right stage to test candidate models and rerankers behind an eval harness and to add cheap graph scoring such as anchor expansion counts or local PageRank over retrieved neighborhoods. fileciteturn8file4 citeturn30academia6turn36academia0

**v3, if and only if v2 shows real bottlenecks,** can introduce more specialized infrastructure. If lexical ranking remains the weak point even after Postgres FTS and metadata tuning, you can revisit ParadeDB or another stronger lexical layer. If hybrid reranking and graph expansion are still not enough for architecture-heavy queries, then late interaction or sparse learned retrieval becomes worth testing. If multiple workers/devices become routine, then PostgreSQL queue claiming with `FOR UPDATE SKIP LOCKED` becomes a clean next step. But those should each be responses to measured pain, not prerequisites for the current repo. citeturn25academia0turn25academia1turn29view0

On model routing, my practical recommendation is a **role registry with cautious defaults**. On memory architecture, the clean layering for this repo is: **rebuildable indexes**, **human-authored project notes**, **reviewable memory candidates**, and **approved durable memory**. `code_chunks` and `text_chunks` should remain derived, rebuildable search artifacts. Generated candidate memories should land in `memory/review/*.candidate.md` with provenance and confidence. Only reviewed candidates should become `memory_items` / `global_memory_items`, with `kind`, provenance, supersession, and approval metadata. That matches your current plan’s push toward `kind`, notes ingestion, and candidate promotion, and it also preserves human-in-the-loop control. fileciteturn8file4

For `agent_memory`, my recommendation is **integrate by bridge, not by merger**. Keep it separate for now. Let ai-orchestrator ingest or sync from its Markdown/SQLite Tier-1 notes through a controlled import path, but do not unify storage engines yet. The reason is architectural discipline: ai-orchestrator first needs its own indexing, search, review, and control loop proven. Once that exists, a sync bridge can map chosen `agent_memory` note kinds into ai-orchestrator note folders or candidate memories without forcing a hard coupling too early. That is a judgment call, but it is the safer one for a solo developer hardening an already multi-surface system.

## Research basis

The evidence-backed part of this report is strongest in four places. First, **syntax-aware chunking** is well supported by Tree-sitter’s official design: incremental parsing plus structural query syntax is exactly what you want for stable multi-language symbol extraction. Second, **hybrid retrieval plus reranking** is still the most practical first answer: BEIR showed BM25 remains a robust baseline and that reranking/late-interaction models often win on quality at higher cost; Sentence Transformers documents retrieve-then-rerank directly; and BGE-M3’s own guidance recommends hybrid retrieval plus reranking. Third, **repo-level architectural questions benefit from graph-aware retrieval**: recent repository papers repeatedly use function-call graphs, dependency graphs, and hierarchical repo maps to reduce token use while improving answer quality. Fourth, **PostgreSQL + pgvector is already enough for a strong local-first v1**, because pgvector gives you dense retrieval and Postgres gives you robust lexical indexing and metadata filtering in one system. citeturn16view0turn16view2turn24academia0turn17view0turn19view2turn30academia6turn36academia0turn36academia2turn36academia3turn10view0turn13view0turn13view1turn10view2turn33view0

The model recommendations are partly evidence-backed and partly judgment. The evidence-backed part is that BGE-M3 is explicitly multi-function (dense + sparse + multi-vector), that Qwen3 Embedding is instruction-aware and dimension-flexible with strong multilingual/code-retrieval positioning, that Nomic Embed Code is a serious code-specific retriever with CodeSearchNet-reported strength, and that Qwen3-Coder-30B-A3B-Instruct is designed for long-context coding and repository-scale use. The judgment call is the deployment ordering: for your repo, I would still keep current embeddings in production while you add evaluation, because benchmark leadership is not the same thing as being best for *your* queries and your schema. citeturn19view2turn20view0turn19view0turn37view4turn21view0turn23academia0

The scheduling recommendations are also a mix of source-backed constraints and practical engineering judgment. The source-backed portion is that PostgreSQL `SKIP LOCKED` is appropriate later for queue-like multi-consumer tables, that NVIDIA exposes monitoring and coarse device controls such as power limits and clocks, and that LM Studio exposes model-management controls at the server layer. ## Risks and open questions

The largest technical risk is **schema migration around embeddings**. Your current docs describe 768-dimensional code and text chunk embeddings in the existing schema, while the most interesting candidates do not all fit that shape cleanly. BGE-M3 is 1024-dimensional, Qwen3 Embedding is flexible, and the Nomic model card does not make dimension compatibility the easy path. My recommendation is therefore explicit: treat new embedders as **versioned profiles** with side-by-side evaluation rather than in-place replacements. fileciteturn7file1 citeturn18view3turn20view0turn19view0

A second risk is **control illusion on the GPU side**. You can pause admission, cancel cooperatively, unload models, shrink batches, lower power limits, and monitor processes; you cannot, in the general case, guarantee a clean per-process VRAM quota for every PyTorch job and LM Studio process using only normal workstation tooling. So the architecture should promise what it can reliably deliver: “background jobs back off when you game,” not “the GPU will never exceed X% utilization under all conditions.” citeturn26view0turn26view1turn26view2turn26view3

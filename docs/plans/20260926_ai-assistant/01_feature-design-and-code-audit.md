## Recommendation

Continue in `ai-orchestrator`, as a single-user, local-first control plane. Keep the Python/FastAPI/PostgreSQL service responsible for identity, persisted state, policy and user-visible lifecycle; the host worker executes scoped local actions; Bun/`aioc` and web UI are clients during migration. Keep model providers behind adapters. Treat provider threads as recoverable convenience state, not the task record.

Use the feature order in the companion plan. Close authentication and default exposure issues before bringing tools or providers onto a network boundary; persist conversation/workspace identity before injecting retrieval; authorize tools before planned unattended runs; measure indexing before replacing embedding models; prove one durable runner before supporting multiple CLI providers.

## Cross-feature contracts

### Identifiers and ownership

- `project_id`: durable knowledge/instructions domain, compatible with existing `projects` UUIDs.
- `workspace_id`: a registered local root or checkout binding: canonical real path, platform, project, Git remote/ref metadata, capability policy, and active state. One logical project can later bind more than one checkout.
- `conversation_id`: project and workspace binding fixed at creation, with explicit audited rebinding if the user changes workspace.
- `turn_id`, `message_id`, `tool_call_id`, `approval_id`, `run_id`, `stage_id`, `step_id`, `attempt_id`: stable UUID/ULID identifiers, unique constraints at writes, and references from audit/events.
- Do not use display names, repo remote strings, provider session IDs, or client-supplied actor strings as authorization identity.

All SQL reads and writes constrain the owning project/workspace in the query itself. Global scope is explicit and independent of project scope. Bind actor identity from authenticated session. Validate ID ownership before returning source paths, memory, sessions, runs, or approvals.

### API and event contract

FastAPI is the migration target for durable project/chat/run/policy APIs; avoid parallel independently-authoritative implementations in `docker/orchestrator/main.py`, the web viewer, and Bun. First leave Bun doing inference and make it call a narrow authenticated persistence/policy API. Move inference only if latency/reliability evidence justifies it. Generate TypeScript types from OpenAPI or shared JSON Schema, and use contract tests for both HTTP and WS.

Every accepted request gets an idempotency key and produces a monotonically sequenced event scoped to the conversation/run. Persist canonical messages, tool proposals/decisions/results, status transitions, checkpoints, and errors. Token deltas can be ephemeral. On reconnect clients present `after_seq`; server replays committed events and the client deduplicates event IDs. Events are notifications, never the sole state store. Enforce a maximum event/message size and explicit schema version.

### Instruction and context construction

Compose context per request from versioned sources: fixed product/runtime policy; user global instructions; project instructions; applicable repository guidance; compact conversation summary and recent messages; approved memory; retrieval evidence; current user message. Record each source ID/version/hash and token count. Resolve instruction discovery/precedence explicitly, make contradictions visible, do not read secrets or full repositories blindly. Repo instruction documents and plans are reference content; policy service controls permissions. Summaries are editable/recomputable, distinguish fact from unresolved assumption, and never replace the message log or repo plan.

User-supplied `ChatGPT_Universal_Instructions_Reference_Spec` reinforces separation between instructions, identity and evolving memory, and that a project reference file alone is not enforcement. This is a useful conceptual input, not a runtime contract for AI Assistant; translate only the portable layering principles.

## Feature designs

### F1 — Service exposure and identity (first implementation work)

**Goal / status.** Keep current local development usable while preventing anonymous network clients from reading state or using tools. In viewer `main.py`, `AUTH_ENABLED=False` by default; `check_auth` is attached to routers conditionally during import, but `/ws/chat` is included outside that condition, the standalone `/ws` route has no auth check, and `system_stats`/`lmstudio` are omitted from the auth-enabled include block. The proxy accepts `/ws/chat` and forwards to Bun without any identity. Compose publishes service ports and mounts `/var/run/docker.sock` into koweb.

**Design.** Create one `AuthContext` dependency/middleware and one WS accept gate. In the current single-user configuration, generate a random local bearer/session secret on first setup, store it outside Git with user-only permissions, provide an explicit local bootstrap and rotation command, and use secure same-site cookies for browser WS authentication (FastAPI supports dependencies/cookies on WS). Pass verified identity through the proxy to Bun/API; do not forward arbitrary client identity headers. Check `Origin` against configured web origins. Bind host ports to loopback by default; remote is a separately documented opt-in behind authenticated TLS/tunnel. Remove the Docker socket from the general web app; if container control remains necessary, route a fixed allowlist through a small host helper with no generic Docker API.

**Tests.** Import-time config tests for auth on/off, all routers protected including model list and system stats, direct `/ws` and `/ws/chat` reject missing/invalid credentials before `accept()`, valid browser cookie and CLI bearer work, disallowed origin fails, proxy cannot downgrade identity, static assets remain accessible only as intended. Compose/config test asserts host port bindings are loopback and no arbitrary Docker socket. Test token rotation and missing-secret startup fail closed for remote mode.

### F2 — Projects, workspaces and repository instructions

**Goal / status.** Create a durable project with one or more approved checkouts and stable global/project instruction layers. Current `detectProject()` discovers Git root on every engine initialization; `setProjectContext()` uses a module-global mutable object. Every WS gets a `QueryEngine`, but context can leak between clients; changing `workingDir` only tests that a path exists and does not recalculate Git root/instructions. Detector loads `CHAT.md` and `CLAUDE.md` only. Its comment says repo tree uses tracked files and excludes `node_modules`, but implementation calls `git ls-files --cached --others --exclude-standard`, so includes untracked files and will include tracked dependencies (the tree snapshot has ~5,431 `node_modules` entries).

**Design.** Extend existing project records, add workspace/checkouts table with canonical path, `project_id`, display label, remote, last observed HEAD, timestamps and capability profile. Keep two path forms: user-entered and canonical resolved path; store canonical path, reject if not authorized. For new workdirs, detect Git root and require explicit workspace registration before write access; read-only temporary browsing can be a separate constrained capability. Replace module-global context with immutable per-turn `ResolvedContext` passed to prompt/tool interfaces. Discover root instructions (`AGENTS.md`, `REPO_LLM_INSTRUCTIONS.md`, `CLAUDE.md`, `GEMINI.md`, and supported AI-Orchestrator project instructions) according to a documented precedence table and provider adapter. Only relevant/authorized files load; path, hash, version, source type and truncation are retained. Project instructions may narrow behavior; they cannot bypass server policy. Fix repo tree by choosing tracked-only `git ls-files` or respecting ignore policy, document behavior, cap bytes and entry count, and exclude large generated/vendor paths independent of tracking.

**Tests.** Concurrent clients initialize different projects and never observe each other’s root/instructions/model setting. Change workspace/reload updates all derived context and invalidates old reads. Unregistered directory may not write; traversal/symlink escape denied. Ignore tests cover tracked and untracked `node_modules`, nested ignore, filenames with spaces/newlines, empty repo, huge repo and non-Git workspace. Precedence fixtures cover multiple instruction files with explicit conflict surfacing.

### F3 — Durable chats and context window

**Goal / status.** Resume correctly after a turn, process or provider failure. Current `QueryEngine` holds `messages` in memory. It appends only `[userMsg]` to JSON after the provider generator ends, does not persist assistant/tool content, and has no method to hydrate history. A failure before append loses the user turn. `SessionStore` synchronously rewrites whole JSON documents without atomic replacement, locking or corruption recovery; `/session` lists only. `currentSessionId` is not a durable selected conversation contract; clear empties in-memory messages but old persisted session remains.

**Design.** Tables: conversations (owner/project/workspace/title/model/status/timestamps); messages (conversation, sequence, role, structured content, turn, provider, status); tool_calls (proposal/input hash/result reference/status); summaries (through-sequence, text, source hash, model and editable state). Save accepted user message before model call; save finalized assistant and tool messages with deterministic sequence/idempotency; represent interrupted generation explicitly. Load full messages or summary plus tail when resumed. `/clear` creates a new conversation or appends a deliberate clear marker; it does not erase history without explicit delete/retention action. Import JSON as incomplete historical transcripts, preserving original file and labeling missing assistant/tool history. Use DB transactions and unique `(conversation_id, idempotency_key)` constraints.

Context builder calculates prompt budget from model metadata, reserves output/tool tokens, summarizes only at a deterministic boundary, excludes superseded turns, and returns a provenance manifest. Log redacted counts/hashes by default, not complete prompt/content. Allow export/import with schema version and round-trip tests.

**Tests.** Full user/assistant/multi-tool round trip, interrupted generation, API timeout after accepted turn, duplicate POST, simultaneous append, process restart, malformed imported JSON, clear/new selection, pagination/replay order, summary edit/rebuild, token cap, and project ownership denial. Fault injection between each DB write proves no dangling assistant/tool references.

### F4 — Scoped file, shell, Git, web and MCP tools

**Goal / status.** Provide real project work tools without granting all host authority. Present tools are directly called inside model loops. `BashTool` executes `bash -c` with full environment, combines output, loses exit status, kills only direct child on timeout/abort, and never removes abort listeners. `READONLY_PREFIXES` is only a concurrency hint and can misclassify compound commands; it is not a permission policy. File read/edit accept caller paths without consulting workspace; glob and grep can leave workspace; grep ignores subprocess exit/error. `WebFetchTool` follows redirects, buffers entire body before truncation and has no SSRF or scheme/IP policy. Logger records system prompt, user message, thinking and complete tool input; even tool output is only character-truncated. Host index job builds shell command strings with DB password and includes command in task description/log.

**Design.** One provider-neutral `ToolBroker` validates JSON schema, authenticated actor, registered workspace, capability, risk level, resource bounds and approval. Tool proposal has canonical action, resource, command/arguments, preview/diff, digest, expiry and one-use nonce. An approval row binds actor, exact digest, run/tool-call and workspace; worker rechecks it at execution atomically. Policy never parses a shell command to guess read-only. Implement file operations using project-relative paths and canonical resolution; no path escape, symlink traversal or time-of-check/time-of-use race (use directory-relative file descriptors or an OS sandbox for untrusted writes). Split shell into approved command profile and explicit interactive shell capability; process groups, cwd, env allowlist, deadline, cancellation, output/CPU/memory caps. Git read and Git mutations are separate capabilities; show diff and require approval for stage/commit/checkout/push. Web search provider and fetch are separate tools; allow only HTTP(S), deny loopback/private/link-local/metadata IP after DNS resolution at connection time, reject unsafe redirects or validate every hop, stream cap/timeout/content type, and write only into workspace. MCP clients/servers are adapters behind same broker, with explicit tool allowlist and per-server credentials; tool discovery never silently grants authority.

Replace shell interpolation for index work with typed payload `{job_type, project_id, workspace_id, code_model_id, text_model_id, options}`. Host worker obtains DB credentials from a protected environment/secret file or its local config, never command args/context/output. Redact paths/credentials in logs; record policy decision, timing, exit code and bounded result hash.

**Tests.** Unit: traversal, symlink and races, malformed schema, limits, cancellation, environment stripping, exit propagation, redaction, private IPv4/IPv6/DNS rebinding and redirect cases. Integration: exact approval digest is one-time, expires, cannot transfer actor/project/action; path mutation after approval invalidates approval. Test shell child/grandchild timeout and tool output truncation. Test commands with quotes/newlines and password spaces never appear in process args/logs. Provider-generated tool-call syntax is always a proposal, never an execution authorization.

### F5 — Code and document index/retrieval

**Goal / status.** Ground answers in inspectable current repo/document evidence. Code path `memory/code_indexer.py` does `repo_path.rglob('*')`, indexes all files recognized by chunker without Git/ignore/size boundaries, stores absolute `str(path)` in rows and has no removal reconciliation. Hash skip is per symbol; unchanged chunks are skipped. `code_chunking.py` parses only top-level Python functions/classes, misses methods/nested declarations and produces unstable duplicate `symbol_name` keys when same symbol repeats; docs are chunked every 2,000 characters with line numbers hard-coded to 1. Text `ingest_pipeline.py` *does* compare content hashes and delete removed files/stale chunk indices; `source_ingestion.py` provides upload/source registry and conversation ingestion. Avoid claiming the text-index feature is absent. Retrieval combines dense/BM25, RRF and optional reranker; BM25 cache loads an entire project’s ready chunks into each process for up to 300 seconds and whitespace-splits, so updates may show stale lexical results and non-English/code tokenization can be weak. `code_search.py` is dense vector only. Models use fixed `vector(768)` columns while catalogs may allow other dimensions; model switch requires a compatible schema/index or isolated versioned rows and full re-embed.

**Design.** Source manifest per workspace/repo/ref/path stores canonical relative path, content hash, file size, language/parser, chunker version, embedding model+dimension, state and last scan. Scan Git tracked files plus explicitly configured non-Git document roots, honor ignore rules, skip secrets/binary/large/generated/vendor files and symlink escapes. Atomic generation strategy: build a new generation, validate all chunks/embeddings, switch active generation, then garbage collect old; for incremental runs, stage per-source rows and atomically replace only after successful processing. Store repo-relative path, commit/ref and line/byte offsets; avoid absolute host path exposure. Stable symbol key includes qualified name/kind/ordinal (or content-key plus source range); retain complete enclosing context for methods and syntax errors fall back to line-aware chunks. Pilot Tree-sitter on TS/JS alongside Python AST; Tree-sitter has official Python bindings/query API, but install only after retrieval evaluation shows benefit. Define language extractor interface and plain text fallback.

Build a golden benchmark from this repository and representative repos; compare vector, lexical, hybrid, reranking, exact vector versus ANN, several chunking schemes and models. Record Recall@k/MRR/nDCG, source accuracy, latency, memory/DB size, token cost and update correctness. Use DB filtered queries by owner. pgvector documents approximate-index filtering can return fewer matches; test iterative scans/partitioning/exact search with actual cardinality. Do not infer quality from the presence of embeddings.

**Failure handling and tests.** Parse and embed failures retain the previous active generation and mark failure with path/error; deletion removes source only when successful scan confirms it. Retry is idempotent; concurrent index requests lease a workspace/source; model migration keeps old results available until new model generation validates. Test ignored and symlink files, empty repo, deleted/renamed/edited file, repeated symbol names, nested Python methods, syntax error, unicode, large/binary file, embedding server unavailable mid-batch, DB disconnect, changed model dimension, deletion reconciliation, cache invalidation across two API processes, cross-project filters and golden relevance. Answer citations resolve back to matching content hash/path/lines.

### F6 — Explicit memory lifecycle

**Goal / status.** Persist user-correctable durable notes separately from source corpus and conversation summaries. `MemoryManager` already adds/searches memory with feedback; API has POST `/memory/search-text`, POST `/memory/search`, `/memory/items`, `/memory/global/search-text`, list/stats/feedback. No `GET /memory/search` exists. `docs/NEXT_STEPS.md` and `memory/PLAN.md` request that endpoint and a `kind` schema phase; `memory/PLAN.md` also suggests startup `initialize_schema` as migration. Current `MemoryManager.add_memory` uses categories, while explicit kind, review state, revisions and chat injection remain absent/unverified. Category and kind must not be conflated.

**Design.** Define approved note as user-visible document with scope, kind, content, provenance, source conversation/turn, created/reviewed/updated versions, confidence/evidence, effective/expiry date and lifecycle state (candidate, approved, superseded, rejected). Existing records migrate to `legacy_unreviewed` with unchanged text, no invented source. Candidate generation is opt-in and displays evidence/diff; only authenticated user can approve/edit/merge/delete. Version edits and tombstones; support export to Markdown-compatible `scripts/agent_memory` frontmatter and round-trip import preview. Retrieval only injects approved, non-expired notes and separately shows candidates. Budget small, dedupe with explicit merge suggestions, scope SQL by project/global; note contents are untrusted data and not policy.

Start with idempotent SQL migration and POST text-search API already present; keep endpoint/methods canonical, update proxy and generated client. Memory retrieval failure is visible but chat can proceed with memory omitted under policy. Add feature flag, per-project/global toggles and an explanation panel showing exact notes/revisions used.

**Tests.** Migration backfills without content loss; approve/reject/edit/merge/version rollback/tombstone; global/project isolation; expiry; empty/low-score results; database/model failure; context token cap; no candidate enters prompt by default; injected notes cite version IDs; export/import round trip. Test aliases/route contract and remove nonexistent GET references.

### F7 — Durable runs, plans, queue and recovery

**Goal / status.** Resume planned repository work through crashes and provider limits while keeping plan/artifacts reviewable. `shared/task_queue.py` is filesystem state layout; `move_task()` writes new path then unlinks old, so operation is not atomic across states/processes despite `docs/TASK_QUEUE_DESIGN.md` requirements. Worker loop can stop on a nonzero worker exit under `set -e` (now fixed on this branch for recorded failures); hard crash can leave `in_progress`. `local_worker.sh` executes arbitrary context command via `bash -lc`, prints full command, and defaults invalid/missing working dir to home. `main.py` accepts `approved=true, approved_by='name'` in request body as “approval”; when approval flag disabled it authorizes with fixed string. Index commands interpolate database password into command line/task description. `docs/NEXT_STEPS.md` runtime host loop remains unverified.

**Design.** Run definition references plan Git path+commit/hash and stable feature/stage/acceptance IDs. DB tables store run, step, attempt, lease owner/deadline, checkpoint, next attempt, blocker, provider session hint and append-only event; uniqueness/idempotency keys at external effects. States include queued, claimed, executing, awaiting approval/input, cooldown, blocked, succeeded, failed, cancelled, needs reconciliation. Claim via one Postgres transaction and `FOR UPDATE SKIP LOCKED` or DBOS queue; Postgres docs explicitly frame SKIP LOCKED for queue-like consumers, not consistent general reads. Lease expiration marks uncertain executing step `needs_reconciliation` before retry. Use a transactional outbox to launch worker/provider after persisted transition. External model/CLI/tool effects are at least once unless upstream supports idempotency: after crash with ambiguous result, inspect provider session/Git diff/tool audit; do not automatically repeat a potentially mutating prompt/action. Human review checkpoint stops exactly before approved effect.

DBOS remains the first spike because it uses Postgres for durable waits and queueing, and official docs provide human-in-loop `send`/`recv` and workflow version upgrade paths. It does not itself make arbitrary shell/provider calls exactly once; every effect needs an idempotency/reconciliation strategy. Compare DBOS with narrow SKIP LOCKED lease runner using same kill/restart/upgrade experiment. Select one execution authority. Keep current filesystem paths read-compatible for kmtui during import/drain; map old task IDs, preserve JSON and logs, stop old writes after cutover. Do not dual-write scheduler state.

**Tests.** Multiple worker claim race (one claim); lease heartbeat/loss; crash before provider, after provider accepted but before local result, after tool effect, after checkpoint, during cooldown, after code deploy; manual approval pause/resume; cancel during subprocess; retry-after parse and capped jitter; moved/deleted branch conflict; provider session expired and handoff to different model; workflow-version change; duplicate outbox; filesystem migration counts; no secret material in task JSON, shell argv or output. Acceptance: uncertain external action enters reconciliation, not auto-replay; checkpoints accurately expose completed vs uncertain work.

### F8 — Provider adapter and PAL decision

**Goal / status.** Use local models and optional remote model/coding CLI with explicit data boundaries. `aioc` currently chooses provider using model ID string prefix and direct backend paths; static web model list includes advertised provider IDs. `cli_integrations` and scripts `agent_sync` exist as adjacent entry points but are not the durable run contract. A provider adapter needs capability/auth/version checks, normalized stream events, cancellation, error/cooldown parsing and session hint. A session ID does not prove server-owned conversation history.

**PAL assessment (checked 2026-09-27).** [PAL MCP Server](https://github.com/BeehiveInnovations/pal-mcp-server) is a real and relevant provider-aggregation/collaboration tool: README describes Claude Code/Gemini CLI/Codex CLI clients, model APIs and OpenAI-compatible custom endpoints (including LM Studio/Ollama), multi-model chat/consensus, planner/review tools and a CLI bridge. Config docs say conversations are kept in process memory and may be purged on MCP disconnect/timeout; that is useful session context but not durable project/task state. PAL’s `clink` docs explicitly warn that shipped CLI presets use permissive flags (`--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `--permission-mode acceptEdits`) that let child agents run tools autonomously. That conflicts directly with AI Assistant’s desired broker/approval boundary if given access to the real worktree. PAL does not supply our workspace/project authorization model, Postgres run/checkpoint state, safe filesystem broker or cooldown-resume contract.

**Recommendation.** Use PAL optionally for human-directed research, second opinions, consensus and code review where the model receives only deliberately selected, non-secret context; run its MCP server locally. For coding, first use read-only CLI role/preset in disposable worktree; never enable PAL’s shipped permission-bypass child CLI flags against the main checkout. An agent that can edit must have an isolated worktree/container and pass through the same approved patch/review workflow. Keep PAL out of the core task scheduler and tool execution authority. Implement AI Assistant’s own thin provider adapters for LM Studio chat, Codex app-server/CLI, Claude CLI and Gemini CLI only when S7 gates need them. If later using PAL inside AI Assistant, expose it as one model-consultation provider/tool behind the broker with feature flag, explicit recipient/provider/data scope, time/cost budget and audit—not as the canonical chat/run provider or as a direct shell agent.

Compare PAL to the product requirement this way: it is useful today for model-to-model *consultation*; it is not the product’s cross-session *work orchestrator*. MCP is a client-server tool/context protocol, not a scheduler or authorization system. Tool grants remain host/application decisions.

**Adapter conformance tests.** Per adapter: absent binary/key, live status, model capabilities and context limits, text+tool event normalization, cancellation, timeout, rate limit/retry-after, malformed output, session resume or explicit unsupported, usage/cost metadata, privacy notice and provider ID persistence. Simulate crash after remote accepted work: no automatic duplicate write. Model router selects by structured capabilities and explicit user choice, not fragile model-name prefix.

### F9 — Index and source ingestion transactions

Uploaded source workflows are present, but `ingest_bytes_as_source()` and `reingest_project_source()` delete existing chunk rows before the new parse/embed completes; an embedder/DB failure can destroy the last good index. The source row can remain status `ingesting`; stored bytes and rows can diverge. Implement generation/version keyed chunks: write immutable source blob; parse and embed to a new `source_version_id`; validate count/model/hash; within one DB transaction switch source's active version/status and active manifest; asynchronously clean previous chunks/blob. Failed staging marks failed and preserves old active version. Ensure `replace_existing` means replacement after successful validation. On delete, tombstone metadata and delete chunks transactionally, then safely remove blob; handle crash with an idempotent garbage collector.

Tests: fail parser, embedding request mid-batch, insert/commit, blob write/rename and GC; concurrently replace same label; dedupe same hash; source IDs and old chunks persist until activation; retry candidate idempotently; state recovers after restart. The existing `source_id` metadata and text pipeline can be extended; do not build a second document store.

### F10 — Web/TUI, setup and observability

Use existing web viewer and `aioc` TUI, not a new UI framework until UI blocks contracts. Project switcher, chat timeline/search/resume, source/citation inspector, reviewed memory view, pending approval/diff, worker health and durable run timeline consume OpenAPI/WS event schema. Display provider, model, external data notice, deadline/cooldown, retry state and stop reason. CLI has safe local first-run `doctor`; never auto-bind network. Startup migration is explicit and outputs DB schema version. Logs structured with correlation IDs, redaction and content opt-in; metrics contain counts/timings and labels, not prompt, credential, private path or content.

Cross-platform support claims are staged: WSL2/Ubuntu first (existing user environment), Windows host and macOS next, Termux as remote client after authentication. LM Studio Windows-host and WSL network paths differ; probe URL and loaded models rather than assuming localhost. Test state backup/restore, path encodings, process cancellation, service restart, offline mode, API compatibility, Python/Bun supported versions and upgrade rollback.

## Tooling and research basis

- Keep Python/FastAPI/asyncpg/PostgreSQL/pgvector and Bun/TypeScript already in the repo. Make cross-language API/event shapes generated/contract-tested.
- Alembic is declared in orchestrator requirements but not a current migration workflow. Use async SQLAlchemy migration runner per Alembic cookbook (Alembic migration API itself remains sync); verify fresh and populated DB migration parity.
- LM Studio documents OpenAI-compatible chat/tools and native REST. Local-first inference path is available, but server/model readiness and model-specific tool quality must be probed.
- pgvector docs caution that approximate vector indexes filter after scan and may return too few scoped hits; test iterative scans and exact-search baseline per scope.
- Tree-sitter's official Python binding exposes parser/language/query, so use behind an extractor interface after a TS/JS benchmark, not as a speculative rewrite.
- PostgreSQL `SKIP LOCKED` is specifically useful to reduce contention for queue-like consumers, but yields an inconsistent general read; claim row inside a transaction and keep normal reads separate.
- DBOS officially supports durable sleep, queues, workflow versioning and `send`/`recv` human response; external process/API side effects still need explicit idempotency or reconciliation.
- OWASP SSRF guidance calls out DNS/IP validation and redirect validation; default URL fetch should not follow unvalidated redirects.
- PAL main branch identifies release 9.8.2 (2025-12-15) and top commit from that date when reviewed; docs support current concept but repository has a long gap since main release despite recent open PR activity. Pin/tag and inspect code/version/dependencies before relying on it. This adds maintenance uncertainty to its non-core status.
